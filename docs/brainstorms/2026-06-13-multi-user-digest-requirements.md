# Multi-user Daily Digest — Requirements

**Дата:** 2026-06-13
**Статус:** отложено / не в roadmap (parked)
**Почему parked (2026-09-26):** персональный on-demand news hub закрывает текущую боль (токены + перегруз); multi-user = БД + биллинг + персонализация — сознательно не двигаемся.
**Тип:** продуктово-архитектурный сдвиг (осознанный пересмотр правила «БД нет / stateless») — только если/когда вернёмся к теме

## Проблема и контекст

Сейчас бот — персональный: один пользователь (`TELEGRAM_USER_ID`), cron шлёт в один `TELEGRAM_CHAT_ID`, всё stateless, БД нет (правило зафиксировано в `AGENTS.md`). Cost LLM-запросов только пишется в лог (`logging.info` в `digest/content/openrouter.py`), никуда не сохраняется.

Нужно расширить бота на **несколько человек**: часть — семья (бесплатно, но cost всё равно трекать), часть — знакомые платно (биллинг руками, без интеграций). Чтобы понимать экономику платных, нужно **сохранять cost по каждому человеку** и уметь смотреть его в боте. Заодно — сохранять сам контент новостей (после sonar) для истории/аудита.

## Терминология

Это **multi-user / subscribers**, НЕ multi-tenant. Тенант — контейнер для группы юзеров с общими данными и границей изоляции между группами (как workspace в Slack). Здесь таких групп нет: каждый человек — самостоятельная единица со своим `chat_id`. Слово «тенант» не используем — оно подтолкнуло бы к лишней архитектуре изоляции.

## Цели

- Обслуживать **единицы–десятки** человек, у каждого свой брифинг.
- **Полная персонализация:** свой город/погода, свой набор тем со **своими запросами** (не только выбор из 9, а кастомный «о чём искать»), своё расписание и часовой пояс.
- **Сохранять cost** каждого LLM-запроса с привязкой к человеку; уметь показать сводку в боте.
- **Сохранять контент новостей** (сырой блок от sonar) по каждому человеку — история/аудит.
- Владеть данными (свой стор, не внешний сервис) — Langfuse остаётся только как observability.

## Не-цели (сознательно вне scope сейчас)

- Self-serve настройка пользователями (команды `/setcity`, задание промптов через бота и т.п.) — конфиг правит только владелец.
- Полностью свободные промпты (юзер контролирует и формат вывода) — кастомизируется только тема/запрос внутри фиксированного скаффолда; формат RU+SUMMARY+LINK неизменен, парсер не трогаем.
- Payment-интеграции — биллинг вручную.
- Публичный onboarding (`/start` для любого).
- Шаринг новостей между людьми — при полной персонализации новости у всех разные, шарить нельзя.

## Принятые решения

### Роли и доступ
- Владелец — единственный админ (по `TELEGRAM_USER_ID`). Пользователи только получают брифы, ничего не настраивают.
- Масштаб: единицы–десятки людей, правки конфига редкие.

### Хранилище — разделение по жизненному циклу
Разные типы данных лежат там, где их удобнее всего трогать:

| Данные | Природа | Где | Как правят |
|--------|---------|-----|------------|
| Конфиг людей | статичный, hand-edited, редко | **env var `USERS_CONFIG` (JSON)** | веб-дашборд Railway |
| cost + контент новостей | пишет программа, копится | **SQLite на Railway volume** | программа (rw), владелец (ro через `/costs` / ssh) |
| Идемпотентность доставки | пишет программа | **SQLite (та же)** | программа |

**Почему именно так:**
- Конфиг НЕ в git — репозиторий публичный, `chat_id` и данные живых людей коммитить нельзя.
- Конфиг НЕ в самой SQLite — файл на volume достижим только внутри контейнера (`railway ssh`); править через ssh неудобно. Env var правится в веб-дашборде Railway — самый удобный ручной способ при малом N.
- Данные в SQLite, а не Postgres — на Railway Postgres это отдельный always-on сервис (~$3–5/мес за RAM 24/7), а SQLite — просто файл, который читает уже работающий процесс бота (≈ только storage, центы). `sqlite3` — stdlib, в духе `AGENTS.md` «stdlib first».

### Схема данных

**Конфиг — env var `USERS_CONFIG` (JSON-массив):**

```json
[
  {
    "id": "anya",
    "chat_id": 12345678,
    "name": "Аня",
    "city": "Da Nang",
    "tz": "Asia/Ho_Chi_Minh",
    "topics": [
      {"id": "ai",     "title": "ИИ",  "prompt": "последние новости про ИИ и LLM", "group": "tech"},
      {"id": "garden", "title": "Сад", "prompt": "новости садоводства в Дананге",  "group": "world"}
    ],
    "schedule": ["08:00", "18:00"],
    "status": "family"
  }
]
```
`id` (юзера) — собственный стабильный ключ владельца (не `chat_id`), по нему связь с БД. `schedule` — локальное время. `status` — `family | paid`.

**`topics` — список объектов, не id из каталога:**
- `id` — стабильный ключ темы *внутри этого юзера* (идёт в `news_fetches.topic`; пространство имён — на юзера, всегда читается вместе с `user_id`).
- `title` — отображаемое имя.
- `prompt` — кастомный запрос «о чём искать»; подставляется в фиксированный скаффолд `digest/content/news/prompt.py` (RU + SUMMARY + до 4 `LINK url | title`). Юзер задаёт только тему, формат вывода неизменен → `parse.py` не трогаем.
- `group` (опционально) — для группировки в сообщениях (`report.py`); при кастомных темах группы становятся свободными.

**Владелец — обычная запись в `USERS_CONFIG`.** Его текущие 9 тем (и их группы из `NEWS_GROUPS`) **переезжают** из `digest/content/news/topics.py` в его `topics` в конфиге. После миграции `topics.py` как каталог-источник-правды **удаляется** — нет отдельного списка тем, всё живёт в конфиге. Новому человеку темы заводишь, копируя/правя руками (например, от своей записи).

**SQLite — `news_fetches` (ядро: cost + контент):** одна строка на (юзер × тема × фетч), пишется в `digest/content/news/fetch.py`, где cost и текст блока уже доступны.

```sql
CREATE TABLE news_fetches (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id  TEXT    NOT NULL,   -- = USERS_CONFIG.id (мягкая связь, не FK)
  ts       TEXT    NOT NULL,   -- ISO8601 UTC
  topic    TEXT    NOT NULL,
  model    TEXT,
  cost     REAL    NOT NULL DEFAULT 0,
  content  TEXT,               -- сырой блок sonar; NULL если тема упала
  ok       INTEGER NOT NULL DEFAULT 1
);
CREATE INDEX idx_nf_user_ts ON news_fetches(user_id, ts);
```

**SQLite — `brief_deliveries` (идемпотентность планировщика):**

```sql
CREATE TABLE brief_deliveries (
  user_id  TEXT NOT NULL,
  slot     TEXT NOT NULL,   -- "08:00"
  date     TEXT NOT NULL,   -- YYYY-MM-DD (локальная дата юзера)
  sent_at  TEXT NOT NULL,
  PRIMARY KEY (user_id, slot, date)
);
```

**Мягкая связь `user_id`:** БД не знает о конфиге; удаление человека из `USERS_CONFIG` НЕ удаляет его строки в БД (история cost/новостей платного клиента должна сохраняться).

### Доставка по расписанию
- Cron бьёт не по фиксированным 8:00/18:00 Da Nang, а **тикает чаще** (порядка раз в 15 мин) → сервер читает `USERS_CONFIG`, по локальному времени каждого решает, кому пора, и шлёт.
- Идемпотентность через `brief_deliveries` (не слать слот дважды).
- Бриф сам по себе LLM не вызывает (как сейчас) → в `news_fetches` не пишется; туда пишется только фетч новостей по кнопке/`/news`.

### Cost в боте
- Команда вида `/costs` — сводка `SUM(cost)` по людям за период (владельцу).
- Langfuse остаётся как observability, но источник правды по cost — своя SQLite.

## Затронутые области кода (ориентир для плана)

- `digest/content/news/fetch.py` — точка записи `news_fetches` (cost + content уже здесь); читает темы из конфига юзера, а не из глобального каталога.
- `digest/content/news/prompt.py` — скаффолд остаётся фиксированным, в него подставляется `topic.prompt` из конфига.
- `digest/content/news/topics.py` — **удаляется**; 9 тем и `NEWS_GROUPS` мигрируют в запись владельца в `USERS_CONFIG`.
- `digest/content/report.py` — группировка по полю `group` из конфига (свободные группы).
- `digest/content/openrouter.py` — `usage_cost()` уже извлекает cost.
- `digest/telegram/` — доставка нескольким `chat_id`, новая команда `/costs`, авторизация владельца.
- `digest/scheduled.py` + `.github/workflows/daily.yml` — переход на тик-модель.
- Новый модуль доступа к SQLite + чтение `USERS_CONFIG`.
- `railway.toml` — конфигурация volume.

## Outstanding Questions

1. **Модель планировщика:** тик GitHub Actions раз в 15 мин + проверка на сервере, ИЛИ отдельные cron-записи на каждого человека? (тик проще в управлении, но чаще дёргает сервер). — решить в плане.
2. **Ретеншен `news_fetches`:** таблица растёт без ограничений. Хранить вечно или чистить через N месяцев (и отдельно — нужно ли дольше хранить cost платных для биллинга)?
3. **Формат `schedule` в конфиге:** фиксированные слоты-строки (`"08:00"`) достаточно, или нужна гибкость (разные дни недели)?
6. **Группировка кастомных тем:** поле `group` свободное — фиксированный набор групп (tech/world/politics) или произвольные строки на усмотрение владельца? Что делать с темой без `group`?
7. **Стабильность `topic.id`:** при переименовании/смене запроса темы сохранять тот же `id` (чтобы история cost/новостей не разрывалась) — это соглашение владельца, не проверяется системой.
4. **`/costs` сейчас или потом:** записывать данные с самого начала (да), но саму команду-сводку можно отложить.
5. **Volume и бэкап:** SQLite на одном volume — нужен ли бэкап (особенно cost платных)? Проверить настройку Railway volume.

## Допущения (требуют проверки в плане)

- Railway volume действительно переживает редеплой, а filesystem без volume — эфемерна. *(не проверено в коде — инфраструктурное допущение)*
- Railway env var редактируется в веб-дашборде и применяется на рестарте. *(стандартное поведение Railway, не проверено)*
- На Railway always-on Postgres-сервис стоит ~$3–5/мес за RAM 24/7, SQLite-файл — практически только storage. *(по публичным ценам Railway 2026, не контракт)*
